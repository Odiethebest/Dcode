# 一、一页速记卡

> 面试前五分钟只看这一页。

## 三句话定位

1. **Dcode 是一个代码理解系统**：索引一个 Python 仓库，用一个有界的 agent 回答关于它的问题，**每一条引用都要通过索引验证，验证不过就从答案正文里抹掉**。
2. **我做的核心是可靠性而不是效果**：诚实性契约（引用可验证、未验证态与未检查态分开）、有界 agent 的控制手段（步数、预算、失败分层、终止条件）、以及一套**能做因果分解的 agent 评测方法论**。
3. **我预注册的主假设判了 `unsupported`，而且是我自己造的消融臂把它测小的**——这是这个项目最值得讲的一段，不是最需要藏的一段。

## 消融分解（必须两行都说）

$$
\underbrace{B4 - B3}_{\text{整个 agent 系统}} = \underbrace{(B4 - B3.5)}_{\text{调用图本身}} + \underbrace{(B3.5 - B3)}_{\text{多步取证}}
$$

| 层 | 调用图 `B4 − B3.5` | 多步取证 `B3.5 − B3` | 比值 |
|---|---|---|---|
| **L2**（跨文件） | +0.0218 | +0.0221 | **1.01×——两者相当** |
| **L3**（架构级） | +0.0226 | **+0.1466** | **6.48×** |

## 30 秒版

> Dcode 是一个代码理解系统：索引一个 Python 仓库，用有界 agent 回答问题，**每一条引用都要通过索引验证，验证不过就从答案里抹掉**。我做的核心是三块：诚实性契约、有界 agent 的控制手段、以及一套能做因果分解的评测方法论。
>

## 2.1 工具设计

**在考什么。** 你给模型的工具，schema 是否严格、边界是否封死、是否考虑过工具结果的可缓存性与可复现性。工具设计差的 agent，失败模式全部集中在"模型传了个奇怪参数"。

**我的证据。**

- **11 个工具，全部走 Pydantic `ArgsSchema`**，注册表在 `apps/agent/src/dcode_agent/tools/__init__.py:22-39`；抽象契约 `tools/base.py:25-38`（`name` / `description` / `ArgsSchema` / `execute` / `cache_key`）。工具**从不直接碰数据库**（`base.py:10-12` 明写），只打网关的内部检索口或本地文件系统。
- **参数校验在进入执行之前**：`tool_call_node` 先 `tool.ArgsSchema(**state.pending_tool_args)`（`graph.py:113`），失败走 `_record_tool_failure` 降级（`:114-117`），**不抛到用户面前**。`read_file` 还有一个 `model_validator` 拒绝 `start < 1` 与 `start > end`（`tools/read_file.py:17-24`）。
- **路径穿越拦截是双层的**：`normalize_repo_relative_path` 先在纯字符串层拒绝绝对路径（`tools/common.py:55`）和 `..` 逃逸（`:63`），`resolve_repo_path` 再用 `is_relative_to(root)` 兜一次（`:74-75`）。**三个碰文件系统的工具各有一个穿越测试**：`test_tools_execute.py:216`（`get_file_outline`）、`:237`（`read_file`）、`:261`（`list_directory`）。
- **`search_code` 的 `mode` 做成工具参数而不是环境状态**——这是我最想讲的一条。工具缓存键是 `tool:{tool}:{repo_id}:{sha256(canonical_json(args))[:16]}`（`packages/shared/src/dcode_shared/cache.py:19-21`）。如果检索模式挂在 arm 级别的环境里而不进 args，**B2 的 dense 检索和 B3 的 hybrid 检索会撞同一条缓存**，两个基线的结果会互相污染。理由写在 `tools/search_code.py:8-11`。
- **工具清单可被 LLM 消费**：`ToolRegistry.manifest()` 把每个工具的 JSON Schema 吐出来（`base.py:58-67`），经 `/internal/tools` 暴露（`main.py:70-77`，带内部鉴权）。

**一句可以直接说出口的：**

> 「工具设计上我做对的一件小事是把检索模式做成工具参数而不是环境变量——因为工具缓存键是由 `(tool, repo_id, args)` 算的，模式不进 args，两个基线就会撞同一条缓存，评测结果直接失效。这不是接口美学，是可复现性问题。」

**缺口。** 工具描述（`description`）是给人读的一句话，**没有针对 LLM 做过 few-shot 或反例说明**——因为我的规划器是规则表，模型根本不看这些描述（见 §3.1）。一旦换成 LLM 规划器，这 11 段描述全都要重写。

## 2.2 预算与终止

**在考什么。** agent 会不会跑飞。上限在哪、谁来判、失败会不会把预算吃光、终止是"决定停"还是"撞墙停"。

**我的证据。**

- **步数上限 14**（`apps/agent/src/dcode_agent/settings.py:14`）。**必须同时说的话**：「从 8 提上来的——B4 的扩展把 8 跑满了，走到上限是截断假象而不是策略」。这句话本身是我最想展示的判断：**当一个 agent 总是终止在预算上而不是终止在决策上，那说明预算在替你做决定，指标测的就不是你以为的东西。**
- **失败也计步**：成功在 `graph.py:168` 递增，失败在 `:189` 递增。所以循环长度上界严格是 14，**反复失败的工具吃不到额外时间**。
- **七条提前退出分支**（除步数外）：

| # | 位置 | 条件 |
|---|---|---|
| 1 | `plan_node` `graph.py:74-77` | `step_count >= 14` |
| 2 | `plan_node` `graph.py:79-83` | `_select_next_tool` 返回 `None` |
| 3 | `decide_after_plan` `:751-752` | `state.error is not None` |
| 4 | `decide_after_plan` `:753-754` | `step_count >= 14` |
| 5 | `decide_after_plan` `:757-758` | `pending_tool_name is None` |
| 6 | `decide_after_plan` `:755-756` | `draft_answer is not None` —— **当前拓扑下不可达**（`draft_answer` 只在 `:239` 赋值，而 `synthesize → groundedness_check → END`） |
| 7 | tool_call 出边 `:789` | `state.error is not None` |

- **`_select_next_tool` 返回 `None` 的全部来源**：`graph.py:810-811`（`expansion == "none"`——**这一条就是 B3/B2 恰好一次工具调用的实现**）· `:911-913`（专用路由已调过同参）· `:915-916`（`_needs_multihop` 为假）· `:918-920`（首次检索无 seed chunk）· `:977`（read_file / find_references / get_file_outline 候选用尽）· `:1009` / `:1021` / `:1040`（调用类问题的三条收敛点）。

**一句可以直接说出口的：**

> 「步数上限是 14，从 8 提上来的。提它的原因不是'不够用'，是我发现最强的那个臂总是终止在上限而不是终止在规划器的判断上——那种情况下你测的是预算不是策略。这是个 off-by-design 的坑，比 off-by-one 难发现。」

**缺口。** 预算只有一个维度（步数）。**没有 token 预算、没有 wall-clock 预算、没有成本预算**——一次查询要是撞上 14 步全是 `read_file`，上下文会很大而我没有任何机制去感知。代码中未找到任何 token 计数逻辑。

## 2.3 失败分层

**在考什么。** agent 出错时是给用户一个降级的答案，还是给一个诚实的失败。这两者的分界你有没有想清楚，还是随手 try/except。

**我的证据。分界画在 `_record_tool_failure`（`graph.py:175-209`）上：**

| 层 | 失败例子 | 处理 | 位置 |
|---|---|---|---|
| **工具层 → 降级** | 参数校验失败 | 记 `state.error` → 出边转 synthesize，**用户仍拿到答案，头部加故障提示** | `graph.py:114-117`；提示 `:699-705` |
| **工具层 → 降级** | 工具执行失败 / 缓存 JSON 解码失败 | 同上 | `graph.py:138-139` |
| **合成层 → 降级** | LLM 流式失败 | 返回 `None` → **退回规则模板合成** | `graph.py:275-282` |
| **排序层 → 降级** | reranker 挂了 | **退回 observation 顺序**，永远返回一个排序 | `graph.py:471-472`，测试 `test_graph.py:1274` |
| **排序层 → 降级** | 证据水合失败 | 该证据 content 留空，排到未打分尾部 | `graph.py:519-521` |
| **基础设施层 → 终止** | registry 缺失 / 未知工具 | 主动 raise → `error` 事件 | `graph.py:105`、`:110` |
| **基础设施层 → 终止** | groundedness 的 DB 查询失败 | 冒泡 → `error`，**答案已流完但没有 `final_answer`** → 前端判 `interrupted` | `graph.py:708-741` 无 try |
| **全局兜底** | 任何未捕获 | `emit_error(code="INTERNAL")`，`finally` 关流 | `main.py:162-165` |

**重试策略逐层**（这是我认为最值得展开的一段，因为它每一层的理由都不同）：

| 层 | 重试 | 理由 |
|---|---|---|
| **工具层** | **零重试** | 工具失败大多是参数或索引问题，重试不会变好；降级到"用已有证据回答"比重试更快也更诚实 |
| **内部 API HTTP** | **零重试** | `tools/common.py:21-27`。同上 |
| **embedding** | **12 次**，指数退避封顶 30s | 索引是离线的，**可以等**；模型 sidecar 冷启动要几分钟。`settings.py:49`，退避 `embedding.py:112`。4xx **立即抛出不重试**（`:102-108`） |
| **reranker** | **3 次** | 查询是在线的，**不能等**。`settings.py:58`。且 **`ReadTimeout` 刻意不在重试白名单里**（`reranker.py:18-22`、`:81-85`）——重试一个慢的 CPU 推理只会往单线程模型服务上堆重复工作，让所有请求更慢 |
| **网关 → agent** | **显式不重试** | `deps.py:76-78` 注释：**重试会重复已经流出去的那半个答案**。流式响应不是幂等的 |

⚠️ **一处我知道的不一致**：agent 的工具缓存读写（`graph.py:130` 与 `:142`）**在 `try` 块（`:132-139`）之外**，所以 Redis 故障会冒泡成 `error`。worker（`pipeline.py:303`）与网关（`query.py:148,159`）都兜了。这是我自己审计出来的，应该改成和另外两处一致。

**一句可以直接说出口的：**

> 「我把失败分成两层：工具层失败是降级——用已经拿到的证据回答，答案头部标注哪个工具挂了；基础设施层失败是终止——发 error，不给答案。分界线是一个具体函数 `_record_tool_failure`。重试策略每一层理由都不一样：embedding 重试 12 次因为索引可以等；reranker 只重试 3 次而且不重试超时，因为重试慢的 CPU 推理只会让单线程服务更慢；网关到 agent 显式不重试，因为流式响应不幂等，重试会重复已经流出去的那半个答案。」

**缺口。** 降级是**单向的**——工具失败之后 agent 直接去合成，**不会换个工具再试一次，也不会告诉规划器"这条路走不通"**。这是 §4 缺口清单的第一条。

## 2.4 上下文工程

**在考什么。** 你往 prompt 里塞什么、塞多少、按什么顺序、以及**你怎么保证塞进去的东西不是你偏心的结果**。

**我的证据。**

- **证据预算 10，对所有 arm 相同**（`graph.py:432`）。**必须同时说的话**：「对所有 arm 相同——约束的是 B4：graph 证据必须挤掉检索证据才能进上下文，不是白送」。理由写在 `graph.py:429-431`：B3 最多只有 5 个检索块，给它更大预算无意义；给 B4 更大预算会让**上下文长度**变成混淆变量。
- **超预算不是删除，是清 content 保 ID**（`graph.py:486-488`，理由 `:483-485`）——超预算的证据**仍然可引用、可验证**，只是不花上下文。这样结构性叙述不会引用到一个不存在的 ID。
- **证据渲染时抹平来源**：检索块、文件摘录、水合后的 graph 结果**用同一个格式渲染**（`graph.py:307-325`，注释 `:308-311`），模型**无法分辨哪条证据是哪个工具产的**，因此不可能基于来源而非内容去偏好。
- **排序特征刻意不含 origin 与 `graph_distance`**（`graph.py:451-454`）。原文：*"A tunable 'prefer graph results' prior fitted on the evaluation set would be a hyper-parameter chosen to make the hypothesis pass; origin stays recorded for diagnostics only."*
- **graph 证据先水合源码再统一排序**（`graph.py:498-529` → `GET /internal/get_chunks`，`internal.py:121-163`）。因为检索结果带代码而 graph 结果只有 `file:line`，不水合的话 cross-encoder 比较的不是"哪个更相关"而是"**哪个有东西可读**"——那是测量偏差，不是模型偏好。
- **单条证据进 prompt 截到 1200 字符**（`graph.py:292`）；水合批量上限 64（`:511`）。

**一句可以直接说出口的：**

> 「上下文工程里我最想讲的是一条负面设计：证据排序的特征里**刻意不放"来源"和"图距离"**。因为我要测的就是调用图有没有用——如果我在排序里给图结果加分，那图赢了就是因为我给它加了分。代价我认：六个图工具里有四个在整个评测里从未产出过任何被引用的证据，**它们赢不过检索结果**。这是我选择承受的负面结果，不是没发现。」

**缺口。** 预算是**条数**不是 **token 数**。1200 字符 × 10 条是一个粗糙的代理，**没有任何地方在数 token**。换更长上下文的模型时这套预算不会自动适配。

## 2.5 幻觉控制 / attribution

**在考什么。** 这是这个岗位最核心的能力项——**你怎么让一个会编造的模型给出可核对的输出**。

**我的证据。四层机制。**

**① 服务端拥有引用命名空间（catalog ID）。** LLM **不能自己写引用**，只能引用服务端在本次请求里发给它的 `[C1]`、`[C2]` 这类 ID（`groundedness.py:33` 的 `EVIDENCE_ID_PATTERN`，目录构造 `graph.py:423-425` / `:437-490`）。任何不在目录里的 ID **直接判失败**（`groundedness.py:184-194`，测试 `test_groundedness.py:277`）。系统 prompt 里有五条强制规则（`llm.py:43-53`），其中 `:44-45` 直接告诉模型：不在目录里的 ID 会被剥离并把分数拉到验收线以下。

**② 普通反引号代码不算引用。** catalog 模式下，`self.client.retrieve` 这种写法是**代码格式化不是证据主张**（`groundedness.py:150-151`），prompt 要求 ID 放在反引号之外（`llm.py:48-49`）。这条很重要——上一版把所有点分内联代码都当引用，导致模型每写一个方法名都在"引用"。

**③ enforce-then-redact，而且分数取抹除前。** 未验证引用**从正文里抹掉换成占位符**（`groundedness.py:407-426`），只有已验证的进 `state.citations`（`graph.py:727-738`）。但**分数是抹除前的比例**（`groundedness.py:403`）：

$$
g(a)=\begin{cases}\dfrac{1}{n}\displaystyle\sum_{i=1}^{n} v(r_i), & n > 0\\[2ex] 0, & n=0 \quad \text{(约定，非推导)}\end{cases}
$$

**这一点是整套机制的关键**：如果分数取抹除后的比例，那答案永远是 100%——**抹除就能洗白**。取抹除前，一个被大量涂抹的答案仍然是低分。

**④ $n=0$ 取 0 而不是 1。** 这是一条刻意选择的约定（推理在 `groundedness.py:257-272`）。取 1 会让"什么都不引用"拿满分——一个学会闭嘴的 agent 能刷出满分。也没有选"从分母里剔除"，因为那样"在不确定的地方就不引用"同样能抬高均值。

**两条脚注为什么要分开**（`groundedness.py:382-386`）：无引用答案得 0.0，与"每条引用都失败"同分。若对无引用答案显示"已移除 0 个未验证引用"，**逐字为真而整体误导**——它暗示有东西被剥掉了。所以两条分开：`:463-478`（什么都没检查过）与 `:481-501`（检查了，移除了 N 条）。

**`symbols.py` 的 `autoescape` 为什么重要**（`packages/shared/src/dcode_shared/symbols.py:56-64`）：符号验证用 SQL `LIKE '%.name'` 缩小候选。Python 标识符里 `_` 极常见，而 `_` 在 `LIKE` 里是**单字符通配符**。不转义的话 `api._get` 会同时匹配 `api.aget`、`api.bget`——**这是守卫里的静默假阳性，是这套系统唯一不能出的错误**。同一个文件还记录了另一件事：符号解析规则曾经有两份（工具一份、守卫一份），导致同一个请求里工具说"在这儿"而守卫说"不存在，删掉"。现在是一份。

**配套指标**：`groundedness = 1.000`，**必须同时说的话**——「B1 的 1.0 是 `baselines/common.py:37` 的字面量，B2–B4 的是实测；且只有配上 `answers_without_citations = 0` 才有意义」。

**一句可以直接说出口的：**

> 「幻觉控制上我做的是把引用的命名空间收归服务端：模型只能引用我这次请求发给它的 ID，不能自己写文件名行号。验证不过的引用直接从正文抹掉。关键的一步是**分数取抹除之前的比例**——如果取抹除之后，那分数永远是满分，抹除就成了洗白。还有一条：一个引用都没有的答案我给 0 分不是 1 分，否则一个学会闭嘴的 agent 就能刷满分。」

**缺口。** 这套机制**依赖一个可枚举、可验证的证据空间**——代码索引正好是。开放域问答没有这个空间（见 §3.3 的迁移性讨论）。另外验证是**存在性验证不是语义验证**：模型引用了一个真实存在的位置，但那个位置**不支持它的论断**，这套机制**抓不到**。这是 judge 该干的活，而 judge 没接。

## 2.6 流式协议与状态机

**在考什么。** 流式输出里，什么时候可以对用户做出承诺。

**我的证据。**

- **七种事件，闭集**（`packages/shared/src/dcode_shared/events.py:13-21`），载荷都是 Pydantic 类型：`thought` / `tool_call` / `tool_result` / `partial_answer` / `citation` / `final_answer` / `error`。线格式 `event: {name}\ndata: {json}\n\n`（`:66-69`，纯 LF），前端按 `\n\n` 切（`client.ts:109`）。
- **三条代码保证的不变量**：
  1. **`citation` 一定在所有 `partial_answer` 之后、`final_answer` 之前**——它们不在图里发，而在 `ainvoke` 返回之后才发（`main.py:124` → `:142`，注释 `:153-155`）。**因为一条 citation 是一个断言，而断言只能在验证之后发**；验证需要完整答案文本，所以"流式盖章"在时序上不可能。
  2. 同一 step 的 `tool_call` 与 `tool_result` 编号一致（`graph.py:1397` 用 `step_count+1`，`:1404` 在 `:168` 递增后用 `step_count`）。
  3. **发出的 `citation` 全部 `verified=true`**（`graph.py:727-738`；`groundedness.py:377,401`）。
- **`interrupted` 是独立第四态**（`useThread.ts:33`）。判定纯粹由事件推导，不看计时器：`error` 优先 → 收到 `final_answer` 才是 `done` → 否则流关了就是 `interrupted`（`:30-34`）。

**为什么必须是独立第四态**（`Turn.tsx:33-39` 记录了这个推理，我认为是整个前端最值得讲的一段）：

> citation 在 `final_answer` 之前一瞬间刷出。所以**一个被打断的 turn 完全可能已经握着若干条逐条已验证的 citation，而它的正文从未经过 groundedness 的抹除**。绑定它们等于给一段没挣到保证的散文盖章。

三种状态是三种**认识论**状态，不是三种严重程度：`done` = 验证跑过且通过 · `error` = 某步失败了 · `interrupted` = **验证从未运行**。所以被打断的 turn：草稿降格显示、标题写 "Draft · never verified"（`Turn.tsx:112-137`）、引用一律不绑定、Sources 页脚不出、状态药丸是**中性灰而不是 amber**——因为 amber 在这套设计里表示"检查了，没通过"（`Trace.tsx:16` 注释明写）。

**一句可以直接说出口的：**

> 「流式协议里我最在意的是：什么时候可以对用户做出承诺。引用事件全部在图跑完之后一次补发，不在流的过程中盖章——因为一条引用是一个断言，断言只能在验证之后发，而验证需要完整答案文本。相应地，一个流断了但没收到终答的 turn 是**第四种状态**，不是 error 也不是 done：它的验证从未运行过，所以草稿降格显示、引用一律不绑定。'没检查过'和'检查了没通过'是两个不同的主张，不能共用一个 UI。」

**缺口。** 全仓**没有任何 live region**（`grep -rn "aria-live\|role=\"log\"" apps/frontend/src` → 0 命中），所以读屏用户听不到流式答案。这不是"没做"——是 Phase 4 退役旧页面时把一个**已经修好的**能力连带删了（加入者 commit `09e2446`，删除者 `7bc6abe`；删前是 `QueryPage.tsx:184` 与 `:234`）。教训是：**退役一个界面时，要 diff 它消费了什么能力，而不只是 diff 死代码。**

## 2.7 缓存与幂等

**在考什么。** 缓存键设计错一个字段，评测结果就是脏的；而这种脏是静默的。

**我的证据。四个键空间**（全部在 `packages/shared/src/dcode_shared/cache.py`，**禁止调用方自己拼字符串**，`:3-5`）：

| 键 | TTL | 构造 | 关键设计 |
|---|---|---|---|
| `embed:{model}:{sha256(text)}` | **永久** | `:13-16` | 内容寻址——同一段代码在不同 repo 里只算一次 |
| `tool:{tool}:{repo_id}:{sha256(args)[:16]}` | **24h** | `:19-21` | **含 args hash**——所以 `search_code` 的 `mode` 必须是参数（见 §2.1） |
| `query:{repo_id}:{sha256(history\x1f query)[:32]}` | **1h** | `:24-52` | **含 history**——否则"谁调用它？"这种上下文依赖的追问会和单轮同问题撞键 |
| `job:{repo_id}` | 完成后 **7 天** | `:55-57` | 进行中无 TTL，完成才设 |

三个细节：

- **`\x1f`（unit separator）作 history 与 query 的分隔符**（`:50`），因为它不可能出现在 JSON 里——边界无歧义。
- **空 history 时 digest 与旧版单轮键逐字节相同**（`:39-41`，测试 `test_schema_roundtrip.py:118`），所以加了多轮之后**历史缓存不会被孤立**。
- **只缓存不含 `error` 的流**（`query.py:72-73`）——`b"event: error\n" not in buffered`。一个失败的回答被缓存一小时，比不缓存糟得多。

**幂等**：`POST /repos` 在 URL 上幂等（`repos.py:63`、`_find_reusable_repo` `:126-151`）。可复用状态是 6 种（`:97-104`），**`failed` 刻意不在其中**——上一次失败正是用户想重试的时候。URL 变体归一化刻意做窄（`:107-123`）：尾斜杠、`.git` 后缀、scheme/host 大小写；**路径大小写保留**，因为把两个真正不同的 repo 合并比留一个重复行更糟。

**一句可以直接说出口的：**

> 「缓存键设计有一条我踩过的坑：工具缓存键是由 `(tool, repo_id, args)` 算的，所以任何影响工具行为的东西**必须进 args**。我的检索模式一开始挂在 arm 级别的环境里，结果两个基线的 dense 和 hybrid 检索撞了同一条缓存——评测结果是脏的，而且是静默地脏。另外查询缓存键含对话历史，否则'谁调用它'这种追问会和单轮同问题撞键。」

**缺口。** 工具缓存 24h **没有基于代码版本的失效机制**——改了 agent 代码必须手动 `FLUSHALL`，否则会拿到旧代码产出的结果。这已经作废过一次评测运行。正确做法是把 agent 的 git SHA 或工具版本号并进键，代码中未找到这样的机制。

## 2.8 Agent 评测方法论 ★ 权重最高

**在考什么。** 这是把"会搭 agent"和"能说清 agent 好在哪"分开的那个维度。招聘方想知道：你有没有能力**在自己不喜欢的方向上得出结论**。

### (a) 五级 baseline 阶梯

| arm | 检索 | 答案路径 | mode | 入 H1 决策 |
|---|---|---|---|---|
| **B0** | 外部 GitHub code search | 模板 | — | 否（不可复现） |
| **B1** | 应用层 BM25 | 模板，groundedness **硬编码 1.0** | — | 否（检索参照） |
| **B2** | dense-only | **共享 agent 合成 + 同一守卫** | `dense_only` | 是 |
| **B3** | hybrid | 同上，**无工具扩展** | `hybrid_only` | 是 |
| **B3.5** | hybrid | 同上，**有 `read_file`/`get_file_outline`，无 graph 工具** | `agent_no_graph` | **否（诊断）** |
| **B4** | hybrid | 同上，**全部工具** | `full` | 是 |

**关键设计**：四个 agent 臂**共用同一个合成模型、同一份 prompt、同一套引用协议、同一个守卫**，差异只来自一张表——`_MODE_TABLE`（`apps/agent/src/dcode_agent/state.py:32-44`），映射 `mode → (检索模式, 扩展策略)`。**这是消融能成立的前提**：如果 arm 之间还有别的差异，差分就不是因果分解。

### (b) 预注册的合取判据

$$
\textsf{H1 supported}\iff \bigwedge_{\ell\in\{L2,L3\}}\Big[\big(C_{B4}^{\ell}-C_{B2}^{\ell}\ge 0.05\big)\wedge\big(C_{B4}^{\ell}-C_{B3}^{\ell}\ge 0.05\big)\Big]
$$

`run.py:545`（阈值）、`:546`（比较层）、`:559-560`（合取）、`:588`（判定）。**四个比较全过才算过。**

结果：`unsupported`。**必须同时说的话**——「四个比较过了三个，B4 vs B3 在 L2 差 0.0061」。

### (c) B3.5 消融的因果分解 —— 这个项目最有价值的一段

`B4 − B3` 在调用图或多步取证**任一变动时都会动**，所以它单独说不出是哪个。B3.5 固定 agent、只拿掉图工具，差分因此可分解（式子见 §一）。

| 层 | 调用图 `B4 − B3.5` | 多步取证 `B3.5 − B3` | 比值 |
|---|---|---|---|
| **L2** | +0.0218 | +0.0221 | **1.01×** |
| **L3** | +0.0226 | **+0.1466** | **6.48×** |

**两条必须一起说的话**：「这是诊断项，代码层面明确排除在判决之外」；「**六倍只在 L3 成立，L2 上两者相当——所以这个分解只在架构级问题上成立**」。

**为什么 B3.5 不进判据**（`run.py:605-616`）：原文 *"promoting an arm into the decision rule would be changing the pass criteria after the fact — the one thing the standing commitments forbid."* 由 `test_run.py:686` 钉住。**这个项目最有价值的发现只能作为 diagnostic 出现，不能改变 `unsupported`。我接受这个代价，因为反过来更糟。**

**消融还暴露了一个更硬的问题**：负责统计"图找到了多少 gold"的工具集合此前包含 `get_file_outline`——而 B3.5 **保留**这个工具。于是"没有图的臂"被记了 12 次图命中、"有图的臂"记 14 次（**必须同时说的话**：这是被废弃的旧集合的值）。**一个分不清有图和没图的度量不是偏高，是测错了对象。**修好后新集合下 B3.5 是 0/0/0、B4 是 4/3/5（**必须同时说的话**：这是重算值，不是任何已提交字段）。修法是把工具集合收成**一个共享 frozenset，两个消费者共用**（`graph_tools.py:58-67`；agent 侧 `state.py:57`，评测侧 `run.py:506`）。

### (d) 方差分析

**合成是随机的**（`temperature = 0.1`，`agent/settings.py:25`），检索是确定的。所以跑三次重复（`run_config.json` → `repeats`）。

- L2 的 `B4−B3` 三次是 **+0.0376 / +0.0057 / +0.0884**。**必须同时说的话**：「极差 0.083 比 0.05 的门槛本身还宽——单次运行分不出真实效应和模型这次碰巧怎么措辞」。
- 差额 0.0061 对应的重复间标准差是 **0.034**（**必须同时说的话**：总体标准差口径；样本口径是 0.042）。**差额只有噪声的 1/5.6。**
- **健全性检查**：B1 三次重复的指标**逐位相同**——这证明方差来自合成而非检索。更细的一条：B2 的 `recall` 也三次相同，只有 `mrr`/`ndcg` 变——说明变的是**引用顺序**不是引用集合。

**结论的形状**：L2 那条**不是"差一点"，是"测不出来"**。要在这个题量下解决这个量级的差异需要约 100 次重复，所以**正确的补救是加题或换语料，不是多跑重复**。

### (e) 两次协议改动，方向相反

| 改动 | 方向 |
|---|---|
| **v1 → v2 计分协议**：让四个 agent 臂用同一条规则（`run.py:83` + `AGENT_BASELINES`） | **对我不利**：v1 下会给出 `supported`，v2 给出 `unsupported` |
| **去掉 groundedness 项**：composite 从四项变三项（`run.py:666`） | **对我有利**：因为被删项在所有 arm 上恒为 1.000，去掉等价于每个 margin 乘 **4/3**，即门槛从 0.050 降到 0.0375 |

第二条我不打算换个说法——`run.py:648-665` 自己写着 *"It is a lowered bar, honestly labelled; calling it anything else would be false."* 能给的辩护只有三条，且都可核对：① 在被用于判决的那次运行**之前**声明并提交；② 四项口径的完整结果**同时发布**在 `h1_report.json` 每行的 `four_term` 里；③ **两种口径都返回 `unsupported`**。第四条我给不出——时序上它确实发生在四次失败之后。

### (f) taxonomy × source 混淆

**5 道 L1 全是人工题，17 道反推题全是 L2/L3，且 gold 集合大一倍**（平均 4.29 个 target / 2.94 个文件，对人工题的 2.12 / 1.38）。所以「B4 在 L3 领先」和「B4 在反推题上领先」**这份数据分不开**。

我测过混淆的方向：调用图的孤立贡献在反推题上是 +0.0183、在人工题上是 +0.0283——**更小不是更大**；引用了至少一条图来源证据的题目比例是 9/16 vs 10/17，几乎相同。但**这不等于排除了偏置**——偏置的形式是"题集里缺什么"，用题集自身的指标测不出来。

这一条是我做这份底稿时才发现的，已经补进 `provenance.json` 的 `limitations`（带 `ADDED AFTER THE RUN` 前缀，说明是从同目录字节重算、无任何 baseline 重跑）。

**一句可以直接说出口的：**

> 「评测方法论上我做的最有价值的一件事，是加了一个我不需要的臂。原本 B4 减 B3 就能报个漂亮数字，但那个差分在调用图或多步取证任一变动时都会动——它说不出是哪个。所以我加了 B3.5：固定 agent、只拿掉图工具。结果是在架构级问题上，图值 +0.022 而多步取证值 +0.147；跨文件问题上两者相当。**这个消融把我自己项目的卖点降级了，而我没有用它去改判决**——B3.5 在代码层面被排除在判据之外，因为把一个新臂加进判据就是事后改规则。」

**缺口。** 评测**完全没有覆盖答案质量**——judge 是 stub，`pairwise_win_rate` 全是 `null`。我测的是"能不能找到正确的代码、引用是不是真的存在"，测不了"解释得对不对、清不清楚"。这是 §4 缺口清单里我标为**最高优先级**的一条。

## 3.1 你的规划器为什么不是 LLM？

> **这题必须一次讲完三层。缺任何一层都会被追到墙角。**

**第一层——这是为实验做的取舍。**

我的规划器是一张手写规则表，不是 LLM（`graph.py:798-812`，路由逻辑 `:815-879` 与 `:882-1040`）。理由不是"LLM 不好"，是**我要测的东西决定了规划器不能是随机的**。

这个项目的核心测量是一个消融：B3.5 是 B4 关掉调用图、其余完全相同，`B4 − B3.5` 因此是调用图的孤立贡献。这个差分要成立，前提是**两个臂之间除了工具集合以外没有别的差异**。而我已经知道，**光是答案合成的随机性就让 L2 的 margin 在三次相同配置的运行之间摆了 0.083**（三次分别是 +0.0376 / +0.0057 / +0.0884，极差比 0.05 的判定门槛本身还宽）。如果规划器也是 LLM，那么两个臂的差异里还会混进"模型这次碰巧选了哪个工具"，我就**没有能力把因果归因到工具集合上**。

规则表让 arm 之间的差异**只来自一张表**：`_MODE_TABLE`（`state.py:32-44`），映射 `mode → (检索模式, 扩展策略)`。附带的好处是这张表可以被单元测试穷举——`test_graph.py` 的 33 个用例里有 12 个是路由测试，LLM 规划器做不到这一点。

**第二层——代价是一个真实的产品缺陷，不是学术取舍。**

规则表的路由靠关键词表：`_needs_multihop` 是 17 个词（`graph.py:1087-1112`），`_call_query_direction` 是 22 个中英文标记（`:1312-1358`）。后果很具体：**一个不含任何关键词的架构问题，会在第一次检索之后直接停止**——规划器返回 `None`（`:915-916`），走进合成。

更糟的是**外部无法区分两种情况**：「规划器判断没有下一步可走」和「规划器没看懂这个问题」，在 SSE 流里长得一模一样——都是一次 `search_code` 之后直接出答案。用户看不出区别，我在日志里也看不出区别。**这是真实的产品缺陷，我不打算把它说成设计。**

**第三层——如果目标是发货，我会怎么改，以及那样之后怎么恢复可测性。**

我会把主路径换成 **LLM function calling**：11 个工具的 `ArgsSchema` 已经是 Pydantic 模型，`ToolRegistry.manifest()`（`base.py:58-67`）已经能把 JSON Schema 吐出来给模型，接口层的改动很小。规则表**退为两个角色**：

1. **fallback**——模型不给工具调用、或给出的参数校验不过（`graph.py:113-117` 已有这条路径）时，用规则表兜一次而不是直接放弃；
2. **护栏**——步数上限、`GRAPH_TOOLS` 的 arm 级禁用（`state.py:57`）、以及"同参数工具不重复调用"（`_has_tool_call` `:1162-1166`）这几条**不交给模型**，因为它们是安全边界不是策略。

那样之后**可测性怎么恢复**，我有具体做法：

- **把规划器的随机性变成一个可控变量**：规划调用单独设 `temperature = 0`，与合成的 temperature 分开配置——现在两者共用 `agent/settings.py:25` 的一个值。这样消融的差分里只剩合成一个随机源。
- **把重复次数从 3 提上去，并先测规划器自身的方差**：跑一次"只换规划器随机种子、其余全固定"的 A/A 实验，量出规划方差的量级，再决定需要多少重复才能压过它。现在的 0.034 只是合成方差。
- **把工具选择序列作为一个可比较的对象记录下来**：现在 `per_question.jsonl` 只记录被引用的证据来源，不记录工具调用序列。要归因规划器，得先把序列记下来。

**收尾一句**：「所以这不是'规则表比 LLM 好'，是'在这个实验设计下 LLM 规划器会让我测不出想测的东西'。要发货就换回来，但换回来之后要先补三件事才能继续做消融。」

## 3.2 这个 agent 怎么防止无限循环 / 失控？

四层，从硬到软：

**① 硬性步数上限 14**（`agent/settings.py:14`），而且**失败也计步**（成功 `graph.py:168`、失败 `:189`）——所以循环长度的上界严格是 14，一个反复失败的工具吃不到额外预算。这个数从 8 提上来，**必须同时说的话**：「B4 的扩展把 8 跑满了，走到上限是截断假象而不是策略」。

**② 幂等去重**：`_has_tool_call`（`graph.py:1162-1166`）用 `(tool, 规范化后的 args)` 判重，同一个工具用同样参数**不会调第二次**。规则表里每一条候选路由都先过这个判断（`:911`、`:944`、`:957`、`:970`、`:987`、`:1026`、`:1034`）。`read_file` 还有一个更宽的版本 `_has_read_covering`（`:1169-1183`）——已经读过覆盖该行的区间就不再读。

**③ 单调推进的规划器**：规划是**基于已有 observation 的确定性函数**（`_select_next_tool` `:798-812`）。它没有"再想想"这种状态——每一步要么给出一个**尚未调用过**的工具，要么返回 `None` 走合成。加上 ② 的去重，规划器**不可能产生环**。

**④ 有界的图内递归**：`find_call_path` 的 BFS 深度上限 `max_depth ∈ [1,6]` 由 Pydantic 校验（`tools/find_call_path.py:25`）；索引侧的基类 BFS 有深度上限 6 加 `seen` 集合（`stages/graph.py:387-401`），**环形继承层次结构不会卡住索引**（测试 `test_graph_stage.py:438`）。

**一句收尾**：「所以失控在这里有三道锁：硬步数上限、参数级幂等去重、以及一个不可能产生环的确定性规划器。第三道是最强的那道——但它也是我为了可测性付出的代价（见上一题）。换成 LLM 规划器之后，前两道锁必须留着，因为它们是安全边界不是策略。」

## 3.3 引用验证这套机制，换成非代码场景还成立吗？

**先给结论**：**部分成立，而且能成立的那部分正好是最难的那部分。**

**成立的三条**（它们不依赖代码这个领域）：

1. **服务端拥有引用命名空间。** 模型只能引用本次请求发给它的 ID，不能自己写来源标识——这条在任何 RAG 场景都成立，而且它挡掉的是最常见的一类幻觉：**引用一个看起来对但不存在的来源**。
2. **enforce-then-redact，且分数取抹除前。** 未验证的引用从正文抹掉，但分数按抹除**前**的比例算（`groundedness.py:403`）。这条的意义与领域无关：**如果分数取抹除后的比例，抹除就成了洗白，分数永远是满分。**
3. **"没引用"和"引用全错"必须能分开。** 前者我给 0 分（`groundedness.py:272`）而不是满分，否则一个学会闭嘴的模型能刷满分；同时用一个独立计数 `answers_without_citations` 把两者分开，因为均值分不开它们。这条在任何要报告 groundedness 的系统里都成立。

**不成立的一条，也是关键的一条**：**代码索引提供了一个可枚举、可精确验证的证据空间**——`file:line` 落在哪个 chunk 里是一次 `start_line ≤ line ≤ end_line` 的 SQL 查询（`groundedness.py:275-301`），答案是布尔的。换成开放域，"这段话是否支持这个论断"**没有布尔答案**。

**所以迁移路径是这样的**：机制的**骨架**（服务端 ID、抹除、抹除前计分、零引用零分）原样搬；**验证谓词** $v(r)$ 从"精确存在性查询"换成一个 NLI 或 LLM-judge 的蕴含判断。代价是 $v$ 从确定的变成概率的，于是：

- 分数从"已验证比例"变成"期望已验证比例"，**需要标注一个 $v$ 自身的准确率**才能解释；
- 抹除阈值不能再是硬的——现在 `groundedness.py:376-380` 是"未验证一律抹除"，换成概率谓词就得有一个置信下界，而这个下界是一个新超参。

**一句收尾**：「骨架能搬，谓词不能。代码这个领域的运气在于'引用是否存在'有布尔答案；换到开放域，这个谓词本身变成一个要被评测的模型，你就从一层评测问题掉进两层。这也是为什么我会说这套东西在**有结构化事实源**的场景——代码、API 文档、法规条文、财报——迁移成本最低。」

## 3.4 你怎么知道你的 agent 变好了？

**这题的正确答案不是"我看指标涨了"，是"我有能力把涨的部分归因到具体改动上"。**

**第一步：定一个不能事后动的判据。** 我的判据是一个**合取**——B4 必须在 L2 和 L3 两层上，同时超过 B2 和 B3 各 0.05 个 composite 点，四个比较全过才算过（`run.py:545-560`）。合取而不是取平均，是因为取平均允许一个层的大胜掩盖另一个层的失败。

**第二步：确认差分能归因。** 光有"B4 比 B3 好"没用——`B4 − B3` 在调用图或多步取证任一变动时都会动。所以我加了 B3.5：固定 agent、只拿掉图工具，把差分拆开（式子见 §一）。结果是在架构级问题上调用图值 +0.0218…（此处必须报准：**L2 上图 +0.0218 / 循环 +0.0221，两者相当；L3 上图 +0.0226 / 循环 +0.1466，六倍多**），**必须同时说的话**：「这是诊断项，代码层面排除在判决之外」。

**第三步：确认涨幅大过噪声。** 合成有随机性（`temperature = 0.1`），所以跑三次。L2 的 margin 三次是 +0.0376 / +0.0057 / +0.0884，**极差 0.083 比 0.05 的门槛本身还宽**。所以我对 L2 的结论不是"差 0.006 就过了"，而是"**这个尺度的效应在这个题量下测不出来**"。健全性检查是 B1 三次逐位相同——证明方差来自合成而非检索。

**第四步：确认度量本身在测你以为的东西。** 这一步是我踩过坑才补上的：统计"图找到了多少 gold"的工具集合曾经包含 `get_file_outline`，而没有图的那个臂**保留**这个工具——于是它被记了 12 次图命中，有图的臂记 14 次。**一个分不清有图和没图的度量不是偏高，是测错了对象。**

**一句收尾**：「所以'变好了'对我来说是四个问题：判据是不是事先定的、差分能不能归因、涨幅有没有大过噪声、以及度量本身是不是在测我以为的东西。第四个是最容易漏的，因为它不会报错。」

## 3.5 这算 agent 算法岗的项目吗？

**不算，我先把边界画清楚。**

**这个项目里没有的东西**：没有训练，没有 loss，没有梯度，没有 RL，没有 reward model，没有 DPO/PPO/GRPO，没有微调，没有蒸馏。**所有模型都是现成调用**——embedding 是 Jina 的推理 sidecar，reranker 是 BGE 的推理 sidecar，合成是 gpt-4o-mini 的 API。我没有改动过任何模型的一个参数。

**有算法含量但要标清归属的一块**：静态调用图解析。它是一套 AST 上的解析规则——导入别名映射、`self.attr` 沿声明基类的广度优先查找（深度上限 6，`stages/graph.py:363-402`）、局部构造对象的类型绑定（只认字面量构造，`:405-445`）。这**属于程序分析（static program analysis），不属于机器学习**。它有真实的工程难度和明确的精度边界——我把它量化了：解析器实际访问到 2615 个调用点，解析成内部符号的是 316 个，**必须同时说的话**：「12% 是无类型推断的纯静态 AST 分析的合理量级，不是 bug」。但它跟"算法岗"关心的那类算法不是一回事，我不会混着说。

**那我做的是什么？**

> **我做的是 agent 的评测与可验证性基建。**

具体是三块：**能不能相信它说的话**（引用可验证、未验证态与未检查态在协议层分开）、**能不能控住它的行为**（步数、预算、失败分层、终止条件）、**能不能说清它到底哪一部分在起作用**（预注册判据 + 消融臂做因果分解 + 方差分析）。

**这块东西是训练侧的上游依赖，不是它的替代品。** 任何要用 RL 或偏好优化去改进一个 agent 的团队，都要先回答两个问题：奖励信号从哪来，以及**你怎么知道涨的那部分是真的**。前者需要一个可信的 judge 与可验证的 attribution，后者需要一套能做因果分解的评测协议。我这个项目做的正是这两件事的工程侧——**它不产生策略，它产生判断策略好坏的能力**。

**一句收尾**：「所以如果你们的岗位是训练 agent 策略，我得诚实说我没有那个经验，我的项目里一行训练代码都没有。但如果岗位是把模型变成一个能上线、能被信任、能被度量的系统——那我做的就是这件事，而且我踩过的坑是'度量本身错了'这一类，不是'分数不够高'那一类。」

## 3.6 你的 agent 有哪些现在做不到的？

七条，我按能不能补上排序，详细见 §四。

1. **工具失败之后不会自我纠错**——失败即降级去合成，不换工具重试、也不告诉规划器"这条路走不通"。
2. **工具调用是严格串行的**——没有并行调用。三个 `read_file` 就是三个串行往返。
3. **没有 MCP**——工具是编译进 agent 的 Python 类，第三方工具接不进来。
4. **没有长期记忆**——服务无状态，历史由客户端每次带上并在网关截断（6 轮 / 2000 字符）。跨会话什么都不记得。
5. **没有真正的 reflection**——`contextualize` 节点只做追问改写，不评估自己的答案。
6. **答案质量完全未测**——judge 是 stub，`pairwise_win_rate` 全是 `null`。**这是我标为最高优先级的一条。**
7. **规划器泛化差**——关键词表路由，见 §3.1 第二层。

**一句收尾**：「这七条里我最在意第六条，因为它不是能力缺失是**盲区**：前六条我知道 agent 做不到什么，第六条我不知道 agent 做得好不好。而且它最好补——`Judge` 的抽象类已经在（`metrics/judge.py:27-36`），接上一个真实模型就能补洞，而且**不会让任何已有结论失效**，因为 groundedness 和检索指标都不经过 judge。」

# 五、三个版本讲述

> 顺序一律是 **诚实性契约 → 有界 agent 控制 → 评测反转**。每个数字带上台账那句话。

## 30 秒

见 §一末（速记卡）。

## 2 分钟

> **一、它是什么，以及我为什么先讲诚实性。**
>
> Dcode 索引一个 Python 仓库，然后用一个有界的 agent 回答关于它的问题。我先讲诚实性契约，因为它是这个系统里唯一不能妥协的部分：**模型只能引用服务端在本次请求里发给它的 ID，不能自己写文件名和行号；验证不过的引用直接从答案正文里抹掉。**关键的一步是**分数取抹除之前的比例**——如果取抹除之后，分数永远是满分，抹除就成了洗白。还有一条：一个引用都没有的答案我给 0 分而不是 1 分，否则一个学会闭嘴的 agent 就能刷满分。
>
> 这条契约一直贯到前端：一个流断了但没收到终答的 turn 是**第四种状态**，不是 error 也不是 done——它的验证从未运行过，所以草稿降格显示、引用一律不绑定。「没检查过」和「检查了没通过」是两个不同的主张。
>
> **二、有界 agent 的控制手段。**
>
> LangGraph 五节点，11 个工具，全部走 Pydantic schema，碰文件系统的三个各有一个路径穿越测试。步数上限 **14**，**必须说的是**——这个数从 8 提上来，因为我发现最强的臂总是终止在上限而不是终止在规划器的判断上，那种情况下你测的是预算不是策略。**失败也计步**，所以上界是硬的。失败分两层：工具层失败降级（用已有证据回答，头部标注哪个工具挂了），基础设施层失败终止（发 error，不给答案），分界是一个具体函数。重试策略每层理由都不同——embedding 重试 12 次因为索引可以等，reranker 只重试 3 次且不重试超时因为重试慢的 CPU 推理只会让单线程服务更慢，网关到 agent 显式不重试因为流式响应不幂等。
>
> **三、评测，以及那个反转。**
>
> 五级 baseline，其中四个 agent 臂**共用同一个模型、同一份 prompt、同一套引用协议、同一个守卫**，差异只来自一张映射表。判据是预注册的合取：两层 × 两个对手，**四个比较全过才算过**。
>
> 结果是 **`unsupported`**——**四个比较过了三个**，B4 对 hybrid+rerank 在跨文件那层差 0.0061。但那条**不是差一点，是测不出来**：三次相同配置的运行跑出 +0.038 / +0.006 / +0.088，**极差 0.083 比 0.05 的门槛本身还宽**。
>
> **真正的发现来自我加的第五个臂 B3.5**：它是 B4 关掉调用图、其余完全相同，所以差分可以拆开。在**架构级问题上**调用图值 +0.022 而多步取证值 +0.147，**六倍多**；但在**跨文件问题上两者相当**（+0.0218 对 +0.0221）。**所以这个分解只在架构级问题上成立。**（**必须说的是**：这是诊断项，代码层面明确排除在判决之外。）
>
> **消融把我自己项目的卖点降级了，而我没有用它去改判决**——把一个新臂加进判据就是事后改规则。这是我最想让人看到的那段判断。

## 2-Minute Version (English)

> **What it is, and why I lead with honesty rather than accuracy.**
>
> Dcode indexes a Python repository and answers questions about it with a bounded agent. I lead with the honesty contract because it's the one part of this system that isn't negotiable: **the model can only cite IDs the server handed it for that specific request — it can't write its own filenames or line numbers — and any citation that fails verification gets stripped out of the answer text.** The load-bearing detail is that **the score is the pre-redaction ratio**. Score it after redaction and every answer is perfect, because redaction becomes laundering. Same reasoning behind scoring an answer with zero citations as 0 rather than 1 — otherwise an agent that learns to say nothing scores full marks.
>
> That contract runs all the way to the UI. A turn whose stream ends without a final answer is a **fourth state**, not an error and not a success: verification never ran on it. So the draft is demoted, and none of its citations bind. "Never checked" and "checked and failed" are different claims and can't share a widget.
>
> **Bounding the agent.**
>
> Five LangGraph nodes, eleven tools, all behind Pydantic schemas; the three that touch the filesystem each have a path-traversal test. Step cap is **14** — and the thing worth saying about that number is that I raised it from 8, because I noticed the strongest arm was terminating at the cap rather than at the planner's decision. When that happens you're measuring your budget, not your policy. **Failures consume steps too**, so the bound is real. Failures are layered: tool-level failures degrade — you still get an answer, built from the evidence gathered before the failure, with a notice about which tool died — while infrastructure failures terminate honestly with an error and no answer. The split lives in one function. Retry policy differs per layer for different reasons: embeddings retry twelve times because indexing can wait; the reranker retries three times and deliberately does not retry on timeout, because retrying slow CPU inference just piles duplicate work onto a single-threaded model server; and the gateway never retries the agent, because a streaming response isn't idempotent — a retry would duplicate the half-answer already on the wire.
>
> **The evaluation, and the twist.**
>
> Five baselines, of which four answer through **the same model, the same prompt, the same citation protocol and the same guardrail** — they differ only by one lookup table. The pass criterion was pre-registered as a conjunction: two reasoning levels against two rivals, **all four comparisons have to clear**.
>
> The verdict is **`unsupported`** — **three of four cleared**; the full system misses hybrid-plus-rerank on cross-file questions by 0.0061. But that one isn't "narrowly missed", it's **not measurable at this suite size**: three identical runs produced +0.038, +0.006 and +0.088 — **a spread of 0.083, wider than the 0.050 bar itself**.
>
> **The actual finding came from a fifth arm I built specifically to spoil my own story.** B3.5 is the full system with the call graph switched off and everything else identical, which lets the difference be decomposed. **On architecture-level questions the call graph is worth +0.022 while the agent's multi-step evidence gathering is worth +0.147 — roughly six times as much. On cross-file questions the two are indistinguishable** (+0.0218 vs +0.0221), so that decomposition only holds at the architecture level. (Worth stating alongside: this is a diagnostic, and it's excluded from the verdict in code.)
>
> **The ablation demoted the headline feature of my own project, and I didn't use it to move the verdict** — promoting an arm into the decision rule would be changing the pass criteria after the fact. That judgement call is the part I most want people to see.

## 8 分钟深挖

> **一、诚实性契约（约 2 分钟）。** 四层机制展开：服务端拥有引用命名空间（catalog ID，不在目录里的 ID 直接判失败）；普通反引号内联代码**不算**引用（否则模型每写一个方法名都在"引用"）；enforce-then-redact 且**分数取抹除前**；零引用取 0 分而非 1 分，并用一个独立计数把"没引用"和"引用全错"分开。再讲一个细节展示这套东西为什么难做对：符号验证用 SQL `LIKE '%.name'`，而 Python 标识符里 `_` 极常见、`_` 在 `LIKE` 里是通配符——不转义的话 `api._get` 会匹配 `api.aget`，**这是守卫里的静默假阳性，是这套系统唯一不能出的错误**。
>
> **二、有界 agent 的控制手段（约 2 分钟）。** 见 2 分钟版第二段，展开：七条提前退出分支、`_has_tool_call` 的参数级幂等去重、以及"确定性规划器不可能产生环"这条最强的锁——同时说明它是我为可测性付的代价，要发货就得换成 LLM function calling，换完要补三件事才能继续做消融（规划 temperature 独立配置、A/A 实验量出规划方差、记录工具调用序列）。
>
> **三、上下文工程里的一条负面设计（约 1 分钟）。** 证据预算 10 对所有 arm 相同（**必须说的是**：约束的是最强的臂，图证据必须挤掉检索证据而不是白送）；超预算清 content 但**保留 ID**，所以结构性叙述不会引用到不存在的 ID；证据渲染抹平来源，模型分不出哪条是哪个工具产的；**排序特征刻意不含来源与图距离**——因为要测图有没有用，就不能在打分里假定它有用。代价我认：六个图工具里有四个在整个评测里从未产出过被引用的证据。
>
> **四、评测方法论与那个反转（约 2 分钟）。** 见 2 分钟版第三段，展开三件事：① 度量本身错过一次——统计"图找到了多少 gold"的工具集合曾包含一个**无图臂也保留**的工具，于是无图臂被记了 12 次图命中、有图臂 14 次（**必须说的是**：这是被废弃的旧集合的值），**一个分不清有图和没图的度量不是偏高，是测错了对象**；② 两次协议改动方向相反——v1→v2 让四个臂用同一条规则，**改完我的结论从 supported 变成 unsupported**；同一批改动里我把 groundedness 从 composite 拿掉，那**确实是降门槛**（等价于 0.050 → 0.0375），我不换说法，能给的辩护只有"事先声明、两种口径同时发布、两种口径都是 unsupported"三条；③ taxonomy 与题目来源在这份数据里**分不开**，这条是我做底稿时才发现并补进产物的。
>
> **五、下一步（约 1 分钟）。**

| 优先级 | 下一步 | 具体做什么 | 能回答哪个现在答不了的问题 |

# 六、数字失忆时的第一性原理兜底

> **规则：数字想不起来时，说它是怎么来的、量级是多少、以及它为什么是那个量级。用推导替代精确值，然后主动说"具体数我要查一下"。**
>
> 这一节里没有一句是"记不清"——那三个字单独成句会让整段陈述失去可信度，而**说得出推导过程反而比背得出数字更能证明你懂**。

|---|---|---|
| 1 | **调用图孤立贡献 +0.022** | 「它很小，跟 agent 循环在跨文件那层基本打平，量级是**百分之二点几个 composite 点**——远小于 0.05 的判定门槛，所以它单独绝对撑不起这个假设。**这个数是 B4 减 B3.5 算出来的**，具体值我要查一下 `h1_report.json` 的 `diagnostics`。」 |
| 2 | **agent 循环贡献 +0.147（L3）** | 「在架构级问题上它比调用图大一个量级——**图是百分之二点几，循环是百分之十几**，所以是六倍多。但**跨文件那层两者是打平的**，所以我只在架构级这么说。具体值在 `diagnostics.per_taxonomy` 里。」 |

> 「这个数我不想说错，让我用它的来路说：它是 **{分子是什么} 除以 {分母是什么}**，量级在 **{数量级}**，之所以是这个量级是因为 **{一句机制解释}**。**具体值我要翻一下 {产物文件 / file:line}。**」
