## Step 3 — 「改进 → 成效」链条

只有同时满足四条才算完整：①改动前状态有出处 ②改动有 `file:line` 或 commit ③改动后状态有出处 ④因果关系在代码或提交记录里有依据，不是事后推断。

### 甲类 · 工程改进（修了缺陷或提升能力，前后可比）

#### 甲-1 · 符号解析规则统一 —— 守卫和工具此前用两套规则

| 要素 | 内容 |
|---|---|
| **前** | 守卫 `_verify_symbol` 用 exact match，工具 `routes/internal.py` 用 exact + dotted suffix。同一请求里工具说「在这儿」，守卫说「不存在，删掉」。**九次单臂运行中，symbol 形式的引用活下来的次数是 0 · 0 · 0**（`results/b4-citation-fix-experiment.md` 结论表，原始臂与 A 臂共六次运行全为 0） |
| **改** | commit `029b9de` "fix(shared): one rule for what a name refers to, applied by the guardrait too"，规则收进 `packages/shared/src/dcode_shared/symbols.py:38-53`，SQL 侧 `:56-64` 只做超集缩小 |
| **后** | 同一实验的 B 臂三次运行：**symbol 形式引用 2 · 2 · 2**（首次存活）；**已验证引用 65 · 62 · 67**（原始臂 54 · 48 · 51）；**抹除标记 12 · 13 · 9**（原始臂 17 · 19 · 21） |
| **因果** | 实验设计写在同一文件：一个 session、一份索引、一对模型 sidecar，**只变 agent 镜像，且逐臂在容器内 grep 验证**。机制另有独立论证：索引里 724 个符号中 719 个带 `src.`/`tests.` 前缀，短名行根本不存在 |

**可以说出口的版本**：「我发现引用验证的守卫和检索工具用了两套符号解析规则，同一个请求里工具说找到了、守卫说不存在。统一成一套之后，**已验证引用从 48–54 条涨到 62–67 条，抹除标记从 17–21 降到 9–13**，而且 symbol 形式的引用第一次活了下来——在此之前九次运行里一条都没有。」

**必须一起说的话**：这九次是**单臂运行，不携带 H1 判定**（`results/README.md` 明标 "not a verdict"）。而且实验报告自己写了「**计数是证据，均值是弱的**」——groundedness 均值的比值是 1.26 和 1.93，在 n=3 下约等于 p≈0.25 和 p≈0.1，报告明说不作为统计显著性。**只引用计数，不引用均值。**

## Step 4 — 诚实结论

**甲类 4 条（其中 1 条下游效果作者自测为零）· 乙类 5 条 · 丙类 4 条（其中 1 条不可引用）。**

**甲类少，而且这是这个项目的性质决定的，不是我漏找了。**

理由有三条，都可查：

1. **这个项目的迭代重心本来就在乙类。**257 个 commit 里，2026-07-30 到 07-31 这两天的密集迭代几乎全是评测口径与实验设计——`b39e756`（统一计分）、`ae72d12`（加对照臂）、`38f8036`（改 composite）、`b17621b`（修 origin 集合）、`5dae9f7`（改计分约定）、`57c9542`（加 file 级计分）。这些改的都是**怎么测**，不是**系统能多做什么**。

2. **甲类的三条都不是「让指标涨」，而是「修掉一个让指标失真或让产品难用的缺陷」。**符号规则统一是修「工具和守卫互相打架」；图证据补源码是修「测量偏差」；测试代码过滤是修「问实现却回答测试文件」。它们的成效是**计数**（引用条数、抹除标记数、tests/ 占比），不是效果百分比。

3. **唯一一条纯能力提升（甲-4，调用解析），作者自己测出下游效果为零，并且记了下来。**这比它有效果更值得讲。

**我没有为了让表格好看把乙类挪进甲类。**乙类里的每一条如果包装成「优化」，第一层追问就会问「优化前后指标涨了多少」，而正确答案是「指标没涨，是我发现之前的测法错了」——那时候再解释就晚了。
